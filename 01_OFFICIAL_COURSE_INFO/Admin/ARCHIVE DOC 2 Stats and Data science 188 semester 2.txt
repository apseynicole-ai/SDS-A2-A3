1. Governing purpose
The application is not a digital textbook, dashboard, quiz game or passive notes website.
Its primary job is:
RECOGNISE → REPRESENT → SELECT → EXECUTE → INTERPRET → VERIFY
and then:
TEACH → REMOVE SUPPORT → TEST INDEPENDENCE → REPAIR ERRORS → RETEST LATER → MIX → TIME → REMOVE THE HTML
That exact learning spine comes from the Brain Project advisory. The advisory also requires that revealed solutions do not establish mastery, mistakes create later repair work, and the end goal is independent closed-book performance.
Definition of success
The HTML succeeds only if the learner can eventually:
1. recognise an unfamiliar problem;
2. determine what random object/parameter is involved;
3. select the correct method without being told the chapter;
4. construct the required representation;
5. execute the method correctly;
6. use Excel/calculator correctly where required;
7. interpret the result;
8. detect unreasonable results;
9. repeat this after a delay;
10. repeat it in mixed and timed conditions.
Use of the HTML itself is never evidence of success.

7. Universal problem-solving component
Every quantitative exercise must use the same underlying six-stage engine.
Stage 1 — RECOGNISE
Prompt:
What is this question actually asking?
Possible structured inputs where appropriate:
* one observation X;
* sample mean Xˉ;
* sample proportion p;
* difference Xˉ1​−Xˉ2​;
* population mean μ;
* population proportion π;
* probability;
* boundary/percentile;
* confidence interval;
* sample size.
Stage 2 — REPRESENT
Require applicable elements:
* symbolic event;
* random object;
* parameters;
* graph;
* tail/region;
* known/unknown variables;
* units.
Example:
P(X̄ > 102.2)
not merely:
“right tail.”
Stage 3 — SELECT
Require method selection before calculation.
Examples:
Normal individual X
Normal sample mean — σ known
Student t — σ unknown
Sample proportion
Difference of means
Uniform
Exponential
Normal approximation to binomial
Z confidence interval
t confidence interval
Bootstrap
FPC
Ask:
Why does this method apply?
at earlier support levels.
Stage 4 — EXECUTE
Only now allow:
* formula substitution;
* arithmetic;
* calculator;
* Excel.
Stage 5 — INTERPRET
Separate answer field.
A correct number but incorrect interpretation must not be marked fully correct.
Stage 6 — VERIFY
Short check:
Does the region match the wording?
Are units consistent?
Is the result between 0 and 1 where probability is expected?
Did you use SD or variance?
Does the final answer address the actual question?
The Brain advisory explicitly requires this universal chain.

14. Deterministic mastery rules
NOT_STARTED
No valid evidence.
________________


UNDERSTAND
Require:
* at least one source-aligned explanation/check;
* correct conceptual decision;
* no solution revealed before response.
Minimum:
understandEvidence >= 1
This is intentionally provisional.
________________


RETRIEVE
Require:
* method/formula/rule reconstructed closed-source;
* no substantial hint;
* at least two separate retrieval items;
* both correct.
retrievalIndependentCorrect >= 2
________________


APPLY
Require:
* at least two different familiar application questions;
* independent;
* method selection correct;
* calculation correct;
* interpretation correct when interpretation is required;
* no solution/hint disqualification.
independentFamiliarPasses >= 2
One successful problem is insufficient.
________________


STABLE
Require all of:
1. APPLY already achieved;
2. one independent changed/unlabelled item correct;
3. one delayed independent item correct;
4. no unresolved material repair on that skill.
apply === true
&& changedTransferPass >= 1
&& delayedPass >= 1
&& openRepair === false
Minimum delayed interval:
36 hours
Preferred scheduler will normally create a 2–3 day gap.
________________


REPAIR
Overrides another state when representative evidence indicates a meaningful error.
Examples:
* wrong statistical method;
* wrong distribution;
* wrong random object;
* wrong tail/region;
* formula recall failure;
* recurring Excel procedure failure;
* incorrect interpretation;
* high-confidence misconception.
A minor one-off arithmetic typo does not automatically destroy all prior mastery.

17. Repair engine
Each meaningful error generates:
ERROR
  ↓
EXPLAIN
  ↓
CONTRAST
  ↓
IMMEDIATE RETRY
  ↓
DELAYED RETEST
  ↓
TRANSFER RETEST
Example: wrong-tail error
Generate:
1. show wording that signalled right tail;
2. contrast right vs left;
3. require learner to shade both;
4. immediate new problem;
5. later different-context tail problem;
6. altered/unlabelled retest.
Example: Excel procedure error
Shorter repair:
1. explain specific input/function error;
2. reconstruct the command;
3. execute a different problem;
4. delayed tool retest.
Clearing REPAIR
One successful immediate retry does not clear repair.
Require:
immediateRepairPass === true
&& delayedRepairPass === true
&& transferRepairPass === true
for high-impact conceptual errors.
Procedure/arithmetic repairs may use:
immediateRepairPass
&& delayedRepairPass

individual X?

difference X̄₁ − X̄₂?

WHAT DISTRIBUTION / METHOD?
Then:
WHAT IS THE CENTRE?
Then:
WHAT IS THE SPREAD / STANDARD ERROR?
Then:
WHAT REGION DOES THE WORDING DESCRIBE?
Then calculate.

The mastery engine
I would provisionally retain the architecture:
NOT STARTED → UNDERSTAND → RETRIEVE → APPLY → STABLE
with:
REPAIR as an override state.
But the Brain Project gets to challenge this before we freeze it.
Crucially, states are evidence based.
For example:
UNDERSTAND
Can identify and explain the idea with support.
RETRIEVE
Can reproduce the rule/formula/process without seeing it.
APPLY
Can solve a new problem independently.
STABLE
Can solve a changed problem again later.
REPAIR
A meaningful error occurred and must be corrected and retested.
Clicking "I understand" earns essentially nothing.
________________


Every concept should follow one teaching cycle
Instead of pages and pages of notes:
1. SEE
Concise explanation.
2. SAY
Explain what the concept means aloud.
3. RECOGNISE
"What kind of problem is this?"
4. CHOOSE
Choose the distribution/formula/procedure before numbers are inserted.
5. SOLVE WITH SUPPORT
Worked example.
6. FADED EXAMPLE
Some steps missing.
7. SOLO
No help.
8. TRANSFER
Same concept, unfamiliar wording/context.
9. RETRIEVE LATER
Question returns later.
That is much closer to learning statistics than producing prettier notes.
________________


The single most important SDS feature: QUESTION ROUTER
Stats questions often become difficult because you don't know what kind of problem you are looking at.
So before calculation, the HTML should train:
WHAT IS THE RANDOM OBJECT?
For example:
individual X?
sample mean X̄?
sample proportion p?
difference X̄₁ − X̄₂?
Then:
WHAT DISTRIBUTION / METHOD?
Then:
WHAT IS THE CENTRE?
Then:
WHAT IS THE SPREAD / STANDARD ERROR?
Then:
WHAT REGION DOES THE WORDING DESCRIBE?
Then calculate.
The existing Chapter 7 formula sheet is already organised around this kind of chain: identify the random object → centre → standard error → conditions → standardise → probability/boundary → interpret.
I want that logic expanded into an interactive decision trainer, not merely left on a sheet.

FORMULA TRAINER
There should be two completely different formula views.
Learning view
Explains:
* what each symbol means;
* when the formula is used;
* when not to use it;
* how to distinguish similar formulas;
* dimensional/logic check.
Retrieval view
Hidden formula.
You must reconstruct/select it.
Then reveal.
Selection drills
The system presents a question without asking you to calculate:
Which formula/model would you use?
This targets a major source of stats errors earlier than arithmetic.

and identify both boundaries.

That matters particularly for an EMSLearn/computer-based format.

TRAP LAB
This should be a major section, not a tiny "common mistakes" box.
Examples:
variance = 36
→ σ = 6, not 36.
one observation
→ use σ.
sample mean of n observations
→ use σ/√n.
above
→ complement.
probability supplied and boundary unknown
→ inverse problem.
population normal
→ X̄ normal for valid sample sizes.
CLT
→ sampling distribution becomes approximately normal, not the population.
And every trap you personally make during practice should be added automatically to My Traps.

* INTERPRETATION
* RUSHING

The source contract very deliberately defines them separately.
A question about standard error cannot be allowed to prove that you can enumerate every possible sample from a tiny population.
Why Codex's coverage audit misses this
Its coverage audit asks approximately:
“How many eligible questions contain this skill ID?”
It does not ask:
“Does this exact question genuinely assess this exact skill?”
So a broad skill array makes the numerical coverage report go green.
Required architectural patch
Do not discard skillIds — they are useful for topic relationships.
Add a second explicit field:
assessesSkillIds: []
or:
evidenceTargets: []
Only assessesSkillIds may award mastery.
Example:
{
  skillIds: ["C6.01","C6.02","C6.03","C6.04","C6.05","C6.06","C6.07"],
  assessesSkillIds: ["C6.07"]
}
for a z-standardisation calculation.
The broad skill list can still mean related to.
It must never mean demonstrated all of these.
This single fix will probably make the claimed 94/94 coverage fall substantially, which is good — then Codex can fill the real gaps rather than hiding them.

3. 🔴 The 13 “validated altered variants” are not genuine transfer questions
Codex's changelog proudly says:
“Added 13 validated VARIANTS” with changed wording/representation evidence.
I inspected how they are generated.
The pattern is essentially:
Unlabelled transfer: [same original application question]
with the answer choices reordered.
For example, the original:
If X=14, μ=10 and σ=2, what is z?
becomes:
Unlabelled transfer: If X=14, μ=10 and σ=2, what is z?
That is not altered wording.
It is the same problem with the words “Unlabelled transfer” stuck in front of it.
Yet its metadata declares:
* changed wording;
* altered representation;
* labels removed;
* changed-transfer evidence.
That directly violates the learning-design requirement that Level 5 should genuinely change surface structure — context, wording, information order, representation, or cues.
Required fix
Each ACTIVE skill family needs at least one actually distinct validated transfer problem, such as:
Familiar
X∼N(10,22). Find the z-score corresponding to X=14.
Transfer
A filling machine produces bottles with mean 500 ml and standard deviation 8 ml. A bottle contains 516 ml. Express its position relative to the process mean in standard-deviation units.
Same operation.
Different surface structure.
That can legitimately count as changed transfer.
Simply reordering answer choices cannot.

4. 🟠 Levels 1–3 still don't actually implement the Brain fading system
The Brain advisory specified that Level 1 should model:
question analysis → representation → method choice → formula → substitution → tool procedure → interpretation → verification.
Level 2 should then genuinely remove selected parts, and Level 3 should leave only structural prompts.
v1.1 currently behaves much more simply.
At Level 1 it mainly tells the learner the answer and asks why an alternative fails.
At Level 2 it displays a sentence claiming:
“the object and route are supplied”
but does not consistently render a proper worked structure containing those supplied elements.
Level 3 largely displays the six headings:
RECOGNISE · REPRESENT · SELECT · EXECUTE · INTERPRET · VERIFY
rather than creating fields that make the learner perform those stages.
Required fix
This does not require a huge teaching engine.
For the important skill families, support objects can simply contain:
scaffold: {
  recognise: "...",
  represent: "...",
  select: "...",
  formula: "...",
  substitution: "...",
  execute: "...",
  interpret: "...",
  verify: "..."
}
Then:
* L1: show all;
* L2: hide 2–4 predetermined components and require responses;
* L3: show only stage labels + blank inputs;
* L4+: problem only.
That would finally make support fading behaviourally real.

5. 🟠 The timed simulation is dynamic in source status, but not properly representative
Codex correctly removed the old hard-coded [6,7] chapter list.
Good.
But its actual question-selection algorithm:
1. sorts the eligible pool by question ID;
2. takes the first eligible item for each response type;
3. fills the remaining places from the beginning of the sorted pool.
So repeated Stage F simulations can repeatedly give the same questions.
It also does not adequately stratify across:
* chapter;
* skill family;
* distribution/method;
* selection vs execution;
* Excel;
* interpretation;
* recent-use history.

6. record overlap percentage.
